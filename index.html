How the numbers are calculated

Throughput is the least certain number in this tool. Tokens/sec per replica depends on batch size, sequence lengths, inference engine and version (vLLM, TensorRT-LLM, SGLang…), quantization kernels, and tensor-parallel communication. Every on-prem and cloud row states whether it used a measured benchmark or the theoretical bandwidth-based estimate. Treat theoretical rows as an optimistic upper bound and replace them with measured benchmarks before quoting.

Workload

req/day          = users × requests per user per day
peak concurrent  = manual input, or derived (default):
                   busy-hour req/s  = req/day × busy-hour share ÷ 3,600
                   seconds/request  = output tokens ÷ target tok/s + 1 s
                   mean             = busy-hour req/s × seconds/request          (Little's law)
                   peak             = ceil(mean + z × √mean)   z = 1.645 / 2.326 / 3.09 for p95 / p99 / p99.9
tokens in/month  = req/day × active days/month × avg input tokens
tokens out/month = req/day × active days/month × avg output tokens
tokens over term = (in + out) per month × 12 × years

On-prem sizing (per model replica)

weights (GB)          = params (B) × bytes/param        FP16 = 2 · FP8 = 1 · INT4 = 0.5
KV per request        = 2 × layers × KV heads × head dim × KV bytes × sequence length
                        (sliding-window layers are capped at the window; MLA models use the latent size)
sequence length       = typical: avg input + avg output   |   worst-case: max context
valid TP sizes        = 1, 2, 4, 8 — must divide attention heads and fit in one node
usable memory         = TP × GPU memory ÷ (1 + overhead %)
max concurrent/replica= floor((usable − weights) ÷ KV per request)
replicas (memory)     = ceil(peak concurrent ÷ max concurrent per replica)
required throughput   = peak concurrent × target output tok/s per request
replicas (throughput) = ceil(required throughput ÷ aggregate output tok/s per replica)
replicas              = ceil(max(memory, throughput[, speed]) × (1 + headroom %))
nodes                 = ceil(replicas ÷ floor(GPUs per node ÷ TP))    — a replica never spans nodes; +1 spare server if N+1
GPUs installed        = nodes × GPUs per node

Every valid TP size is evaluated; the layout needing the fewest nodes is used (ties go to the faster per-request layout). If any layout has a measured benchmark, only benchmarked layouts are considered. If the model does not fit in one node, 2- or 4-way pipeline parallelism across whole nodes is tried.

Throughput: benchmark first, theoretical estimate as fallback

A row in benchmarks.json is used when GPU, model, precision, TP and PP match exactly. Otherwise, unless you choose "benchmark only", the app uses a theoretical bandwidth-based (roofline) estimate, always labelled as such:

bandwidth   = TP × HBM TB/s × bandwidth efficiency %
compute     = TP × dense TFLOPS (FP8 if supported, else FP16) × compute efficiency %
step time(c)= max( [min(weights, active weights × c) + c × KV at avg position] ÷ bandwidth ,
                   c × (1 + input/output ratio) × 2 × active params ÷ compute )
per-request tok/s = 1 ÷ step time        aggregate tok/s = c ÷ step time
c*          = largest concurrency per replica that fits in memory AND meets the per-request speed target
replicas (speed) = ceil(peak concurrent ÷ c*)

Not modeled: TP all-reduce overhead, scheduler/batching inefficiency, speculative decoding, prefix caching, time-to-first-token targets.

On-prem cost over term

server capex   = nodes × node price (all-in, or base + GPUs × GPU street price)
network/storage= % of server capex, or $ per node
support        = server capex × support %/yr × years
power          = nodes × node kW × load factor × PUE × 8,760 h × years × $/kWh
colo (optional)= nodes × node kW × $/kW-month × months
optional       = install, financing, software $/GPU/yr, ops FTE, residual value credit
monthly        = total ÷ months (straight-line)
$ per 1M tokens= total ÷ tokens over term × 1,000,000

GPU cloud

GPUs billed = same replicas/TP as on-prem, packed into the provider's instance size
reserved    = GPUs × reserved $/GPU-hr × 730 h/month (billed 24/7)
on-demand   = GPUs × on-demand $/GPU-hr × active hours/month

API

effective input $/M = (1 − cache hit %) × input + cache hit % × cached input
monthly             = (input tokens × effective input + output tokens × output) ÷ 1M
                      × (1 − batch share % × batch discount %)

Same-model rows (hosted open-weight providers) are directly comparable with self-hosting. Closed models are shown as a separate reference group; they are a different model, not a like-for-like quality comparison.

Utilization: why on-prem wins or loses

average utilization = average output tok/s over the month ÷ output capacity of all installed replica slots
fully-utilized $/1M = $/1M × utilization

Self-hosted capacity is sized for the peak and paid for around the clock; API providers pool many customers, so their price follows volume. On-prem wins when utilization is high enough — which happens at higher volume (bursts shrink relative to the average) and with flatter traffic (24/7 or mixed batch workloads). Every on-prem and cloud row shows its average utilization, and the math panel shows the fully-utilized cost.

Hybrid: owned baseline + pay-per-token overflow

hourly traffic = bell curve around midday whose busiest hour carries the busy-hour share (≤ 4.2% = flat 24/7)
mean concurrency in hour i: c_i = requests/day × share_i ÷ 3,600 × seconds per request
owned capacity K (concurrent requests) = installed throughput ÷ target tok/s per request
served on owned GPUs in hour i = E[min(X, K)], X ~ Poisson(c_i)      (normal approximation when c_i ≥ 30)
owned share of tokens = Σ served ÷ Σ c_i
hybrid monthly = owned servers (sized for K with the same headroom / N+1 as on-prem) + all-API monthly × (1 − owned share)
K is tried from 0% to 100% of peak in 5% steps; the cheapest mix is reported

The Analysis summary verdict names the lowest-cost architecture: Strong on-prem or Likely on-prem candidate (owning is cheapest; "likely" when the pessimistic end of its range is not), On-prem + API for bursts (owned servers sized below the full peak carry 97% or more of tokens; an API absorbs rare spikes), GPU cloud candidate, Hybrid candidate, Near breakeven (paying per token is cheapest but owning catches up within 3× today’s usage) or API candidate. The breakeven sentence separately says when owning crosses the same-model API. Confidence drops one level for each of: a theoretical throughput estimate, a placeholder server price, and default operating assumptions (power load, support, networking).

The verdict reads "Hybrid candidate" when owning GPUs for part of the peak (more than 0% but less than 100%) and sending the rest to the API is at least 5% cheaper than all-API, all-owned and the cheapest GPU cloud option. Often the owned GPUs carry nearly all tokens and the API only absorbs rare bursts, which avoids buying servers for a peak that seldom happens. Owned GPUs use the same headroom and N+1 settings as on-prem, so 100% owned on the hybrid chart equals the on-prem option. It assumes requests can be routed to either owned GPUs or the API (e.g. through a gateway) and that the same model runs on both.

Breakeven

Users are scaled from 0.02× up to 2,000× your profile, keeping per-request shape fixed. With derived peak concurrency, the peak is recomputed at each volume, so bursts shrink relative to the average as usage grows; a manually entered peak scales linearly instead. For each volume the cheapest option in each category is plotted. On-prem and reserved cloud are step functions; API is linear. The crossover is the lowest volume above which on-prem stays cheaper for the rest of the range.

Data provenance

Every seeded number carries source, as_of and status:

  • estimate from a public source on the as_of date; all seeded values are estimates.
  • placeholder low confidence; replace with a quote or measurement. Results that use placeholders show a ⚠ count.
  • override edited in this browser via the Data editor.

No option is favored by default: all feasible options are listed, alphabetically unless you sort by cost.
