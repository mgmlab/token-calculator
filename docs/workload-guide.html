Workload input guide

How to gather AI Inference Economics Calculator inputs from a client

← Back to calculator

Most clients don't know their token counts. They do know their users, use cases and documents. This guide turns those answers into calculator inputs. When in doubt, estimate a range and run the calculator at the low and high ends. The answer often doesn't change the recommendation.

Rules of thumb: 1 token ≈ 0.75 English words ≈ 4 characters. One page of text ≈ 500–650 tokens. A 30-minute meeting transcript ≈ 6,000–8,000 tokens.

Users

Count the people who actually use the application in a typical month, not licensed seats.

Ask: "Who will use this, and what share of them will use it weekly?" Typical adoption for internal copilots is 30–60% of eligible staff after 6 months.

For customer-facing apps, use monthly active users (MAU) from their analytics.

Requests per user per day

Count model calls, not user clicks.

  • Simple chat: one message = one request. Typical users send 5–20 a day; power users 50+.
  • RAG (search over documents): often 2–3 calls per question (query rewrite, answer, sometimes a check).
  • Agents / tool use: 3–10+ calls per task, because each step is a call.
Ask: "How many questions or tasks does a typical user do per day?" Then multiply by calls per task.

If they have a pilot, the provider dashboard or gateway logs give this exactly: total requests ÷ active users ÷ active days.

Avg input tokens

Everything sent to the model on each call:

ComponentTypical size
System prompt / instructions300–2,000
User message30–300
Retrieved documents (RAG)chunks × chunk size, e.g. 5 × 500 = 2,500
Conversation historygrows each turn; often capped at 2,000–8,000
Tool definitions (agents)200–1,000 per tool set

Add the components. Typical results are 1,000–3,000 for chat, 3,000–8,000 for RAG, and 10,000+ for document analysis.

Avg output tokens

Base it on the length of a typical answer: short answers 150–400, summaries 200–500, drafted emails or reports 500–1,500, generated code 300–2,000.

Reasoning models also produce hidden "thinking" tokens. These can be 2–10× the visible answer, so include them.

Active days per month

21.7 for weekday business use, 30.4 for customer-facing or always-on systems.

Peak concurrent requests

This is the most important sizing input: it drives how many GPUs you need. It is the number of requests being generated at the same instant during the busiest period. Estimate it with Little's law:

peak concurrent = peak requests per second × seconds per request
seconds per request ≈ avg output tokens ÷ target tok/s   (+ ~1 s for the prompt)

Peak requests per second is roughly the daily requests squeezed into the busy hours. For business use, about 20–25% of a day's requests often land in the busiest hour:

peak req/s ≈ (users × requests per user per day × busy-hour share) ÷ 3,600
Ask: "When is usage heaviest?" (e.g. Monday 9–10 am, month-end close). "Any events that spike usage?"

The calculator does this for you when Peak concurrency is set to "Derive from traffic pattern" (the default). Enter the busy-hour share: 4% for flat 24/7 traffic, 12.5% for traffic spread evenly across an 8-hour day, 15–20% for a typical office peak. It then adds a burst allowance (99th percentile by default). Switch to manual only when you have a measured peak from a pilot.

The calculator warns if your peak is below the 24-hour average implied by the volume. A peak far above the average (10–30×) is normal for business-hours use. It is also the main reason self-hosting can cost more than an API at low volumes.

Target output tokens/sec per request

How fast text streams to each user. People read at about 5–10 tok/s. Chat products feel responsive at 20–50 tok/s. Batch and back-office jobs don't need streaming, so a lower target (5–10) cuts hardware.

Max context length

The largest single request to support (input + output). Examples: the biggest contract someone might paste in, or the longest chat before history is trimmed. It must be ≤ the model's limit. Common settings are 8K, 32K and 128K tokens.

Model and precision

Pick the smallest open-weight model that passes the client's quality bar on real tasks, since model size drives cost more than anything else. FP8 is the usual choice for production on current GPUs. Use INT4 when memory is tight, and only after a quality check. Leave the KV cache at FP16 unless the inference engine supports FP8 KV (vLLM and TensorRT-LLM do).

Headroom, N+1 and term

Headroom covers growth and bursts: 20–30% is typical, more for fast-growing rollouts. Turn on N+1 (one spare server) when the application is business-critical, so a server failure or maintenance window never drops capacity below the need. Choose a 3-year term unless the client depreciates hardware over 5.

Cloud active hours per month

For on-demand GPUs only. Use 730 for always on. If the client will shut capacity down outside business hours, use 12 h × 21.7 days ≈ 260. Reserved capacity is always billed 24/7.

API caching and batch

Cached-input share: the part of each prompt that repeats across calls, such as the system prompt, tool definitions, or a shared document. If a 1,500-token system prompt repeats on a 2,500-token input, about 60% of input can be cached.

Batch share: the share of traffic that can wait hours for results, e.g. overnight document processing, classification or bulk summaries. Interactive chat is 0%.

Worked example: internal knowledge assistant

Client says1,200 employees; expect about half to use it; ~8 questions a day; answers cite 4–5 policy passages; business hours only; busiest 9–11 am.
Users1,200 × 50% = 600
Requests / user / day8 questions × 2 calls (rewrite + answer) = 16
Avg input tokens800 system + 60 question + 5 × 450 passages + 600 history ≈ 3,700
Avg output tokens350
Active days21.7
Peak concurrent600 × 16 × 25% ÷ 3,600 = 0.67 req/s × (350 ÷ 25 + 1 s) ≈ 10 → round up for bursts: 20

Discovery questionnaire (copy into your notes)

  1. What will the application do? (chat, search over documents, drafting, summarization, agents / automation)
  2. Who uses it, how many are eligible, and how many do you expect to use it weekly?
  3. How many questions or tasks per user per day? How many model calls does each task make?
  4. What goes into each request: instructions, documents (how many, how long), chat history?
  5. How long is a typical answer? Are you using a reasoning model?
  6. Business hours only, or 24/7? When is the busiest hour, and how busy is it?
  7. How fast must answers appear? Is streaming required?
  8. What is the largest document or conversation it must handle?
  9. Which models are approved or preferred? Any data-residency or on-prem requirements?
  10. Is there a pilot? If so, export request counts and token usage from the provider dashboard or gateway logs. That replaces most estimates here.
  11. Growth expectations over the next 12–36 months?
  12. Can any work run as overnight batch jobs?
