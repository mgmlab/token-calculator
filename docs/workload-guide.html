Usage

Users Main

Who will use this, and what share will use it weekly?
Internal copilot: 30–60% of eligible staffCustomer-facing: monthly active users

Count people who actually use it in a typical month, not licensed seats. For batch work, think of “users” as sources or feeds.

Requests per user per day Main

How many questions or tasks a day? How many model calls does each one make?
Chat 5–20, power users 50+RAG ×2–3 calls per questionAgents ×3–10 calls per task

Count model calls, not clicks. With a pilot, use the gateway or provider logs: total requests ÷ active users ÷ active days.

Avg input tokens Main

What goes into each request: instructions, documents (how many, how long), chat history?
Chat 1–3KRAG 3–8KDocument analysis 10K+
Typical components

System prompt 300–2,000 · user message 30–300 · retrieved passages (e.g. 5 × 500 = 2,500) · conversation history, often capped at 2,000–8,000 · tool definitions 200–1,000.

Short answers 150–400Summaries 200–500Drafts and reports 500–1,500Code 300–2,000

Reasoning models also generate hidden “thinking” tokens, often 2–10× the visible answer. Include them.

Performance

Peak demand (busy-hour share) Advanced

When is usage heaviest (for example Monday 9–10 am or month-end close)? Any events that spike it?
Flat 24/7 4%Even over an 8-hour day 12.5%Typical office peak 15–20%

Peak demand decides how many GPUs are needed, and it’s the main reason owning costs more than an API at low volume: servers are sized for the busiest minute but paid for around the clock. The calculator works out the peak from the busy-hour share and adds a burst allowance. Switch Peak concurrency to manual only when a pilot gives a measured peak.

How the calculator estimates it 
peak requests/sec ≈ users × requests per day × busy-hour share ÷ 3,600
seconds per request ≈ output tokens ÷ target tok/s + about 1 s
peak concurrent ≈ peak requests/sec × seconds per request, plus a 99th-percentile burst allowance

Response speed (tok/s) Advanced

How fast must answers appear? Do they stream?
Reading speed 5–10Responsive chat 20–50Batch 5–10

Faster targets need more hardware; batch and back-office jobs can accept less.

Max context length Advanced

What is the biggest document someone might paste in, or the longest conversation before history is trimmed?
8K32K128K

Input plus output for the largest single request. It must fit the model’s limit.

Model & sizing

Model & precision Main

Which models are approved or preferred? What quality bar does the use case need?
Production FP8Memory-tight INT4 after a quality test

Model size drives cost more than anything else, so start from the smallest model that meets the bar. Leave the KV cache at FP16 unless the inference engine supports FP8 KV (vLLM and TensorRT-LLM do).

Headroom, N+1 and term Advanced

How fast will usage grow? Is it business-critical? Over how many years is hardware depreciated?
Headroom 20–30%N+1 = one spare server if criticalTerm 3 or 5 years

Acceptable wait in the busiest hour Advanced

In the busiest hour, how long can a request wait before it starts? Would a few seconds’ delay at peak be fine if it saves buying servers?
Customer-facing chat: no waiting or 5 sInternal tools: 30 sAgents, background jobs: 2–10 min

Buying enough servers that nobody ever waits means paying for capacity used only in the busiest minutes. Allowing a short wait lets a smaller setup cover the workload: requests beyond capacity queue briefly instead. The calculator estimates the busiest-hour wait for each server setup (95% of requests start within the time shown) and picks the cheapest one within this limit. The Hybrid section’s table shows the whole menu: cost per year against how long people would wait.

Discovery questions

Use case

  • What will the application do: chat, search over documents, drafting, summarization, agents?
  • Which models are approved or preferred? Any data-residency or on-prem requirements?
  • Which API providers are approved to buy from?

Users & volume

  • Who uses it, how many are eligible, and how many weekly?
  • How many questions or tasks per user per day, and how many model calls each?
  • Growth expected over the next 12–36 months?

Requests

  • What goes into each request: instructions, documents (how many, how long), chat history?
  • How long is a typical answer? Reasoning model?
  • What is the largest document or conversation it must handle?

Timing & operations

  • Business hours only, or 24/7? When is the busiest hour?
  • How fast must answers appear? Streaming?
  • Can any work run as overnight or queued batch jobs?
  • Is there a pilot with request and token logs? (That replaces most estimates.)
  • Existing data center and GPU operations staff?
